# TapNow 备份插件自审计

审计日期：2026-09-08（Europe/Berlin）

## 已验证

- 扩展可以在已登录 TapNow 页面注入内容脚本，并从页面入口打开独立备份中心。
- 节点、连线使用游标分页；真实单画布测试得到 1,238 个节点、1,242 条连线。
- 递归发现当前值、备选、历史和 `fileId` 引用；真实测试得到 5,776 条引用、2,489 个唯一下载目标。
- 媒体请求在后台使用 TapNow `Referer`，并支持 file-ID 派生地址、Range 分段、重试、SHA-256 校验和内容寻址保存。
- 单个资源失败不会阻塞队列；失败记录可供后续增量运行复查。
- 单元测试 41 项全部通过，Chrome MV3 构建成功。
- 同一登录会话的真实执行器已保存并复核 2,457 个文件，共 16,093,586,301 字节；每个文件通过存在性、长度和 SHA-256 校验。

## 本轮已经修复

- 不能使用页面上下文 `fetch` 下载媒体的问题：改为扩展后台/浏览器上下文请求并带主站 Referer。
- 只有 `fileId` 没有 URL 时直接失败的问题：加入 `/api/conversation/storage/uploads/{fileId}` 派生地址恢复。
- 分页游标重复导致死循环的问题：检测重复游标并把结果标记为不完整。
- 404 对象与普通瞬时网络错误的状态语义：运行脚本会把 404/410 归为 `unavailable-after-recovery`，其他错误保留为 `retryable`。
- 真实测试报告的查看：新增独立本地查看器，报告接口会从 `assets.ndjson` 重新汇总状态，避免旧报告中的状态字段掩盖实际结果。

## 当前不能验收的事项

1. **扩展 UI 的大规模目录写入**：本次 16.09 GB 结果由真实登录会话执行器保存，不是扩展备份页通过 File System Access API 全量写入，因此不能宣称扩展 UI 已完成同等规模的端到端验收。
2. **真实磁盘预算**：扩展页面当前只能使用浏览器 `navigator.storage.estimate()`，它不是用户选择目录所在文件系统的剩余空间。独立执行器使用 `statfs`，但纯 Chrome 扩展无法直接读取真实磁盘剩余空间。
3. **全工作区/项目枚举**：本次只测试了一个画布；尚未证明工作区全部画布、子项目和隐藏/归档范围的枚举完整。
4. **增量同步和 tombstone**：checkpoint 基础已存在，但真正的跨运行变更检测、删除对象标记、用户维护的“无需下载名单”还未完成。
5. **异常写入恢复**：尚未完成扩展端浏览器重启、目录权限撤销、进程中断后的实机恢复测试。

## 验收结论

本插件已达到“真实发现与下载链路可行、失败不中断、结果可审阅”的阶段，尚未达到“纯扩展 UI 在任意用户目录完成全工作区资产保管”的最终验收标准。独立查看器不依赖扩展：默认只监听 `127.0.0.1`，需要从 Mac 或 Windows 访问时可用 `HOST=0.0.0.0` 启动，并通过服务器域名和端口访问；备份目录仍由服务器端启动参数明确指定。跨公网暴露前应加访问控制或 SSH 隧道。
