# 真实账户备份测试记录

测试日期：2026-09-08（Europe/Berlin）

## 范围

使用已登录的目标 TapNow 账户，在 VNC 中的 Chromium 里选择了一个团队项目下
的单个根画布作为首轮真实样本。测试不读取或保存密码、Cookie、Bearer token，
也没有执行生成、编辑或删除操作。

服务器根文件系统测试前可用空间约 113 GiB，按用户授权的三分之一规则，本次
下载预算约 38.8 GiB（另预留安全余量）。

对象库按内容哈希去重，节点/字段/历史/备选引用另行保存，因此引用数大于
实体文件数是预期行为。

## 发现并修复的问题

1. 页面上下文对 `files.tapnow.media` 批量 `fetch` 全部报
   `TypeError: Failed to fetch`，不能把页面 fetch 当作媒体下载方案。
2. 扩展后台/本地请求使用 `Referer: https://app.tapnow.ai/`、不携带主站
   Bearer 后，可以得到 `200` 完整响应及 `206 Content-Range` 分块响应。
3. 只有 `currentSourceFileId` 没有 URL 的对象不能直接判定失败。按
   `/api/conversation/storage/uploads/{fileId}` 反查后，大部分成功下载。
4. 剩余 32 个 file ID 路径稳定返回 404，已执行有限重试，记录为
   `unavailable-after-recovery`，不会阻塞其他对象，后续仍可通过增量运行复查。
5. 扩展最初在 VNC 中被 Chrome 禁用，因为开发者模式关闭；打开开发者模式并
   重载后，TapNow 页面内容脚本正常注入，页面内“备份”按钮可真实打开备份中心。

## 结论

本次证明了以下链路可用：真实登录态、真实大画布分页、全资源引用发现、媒体
Referer 边界、file ID 原始路径反查、Range 下载、内容哈希校验、失败不中断、
checkpoint 恢复和页面内备份入口。

本次尚未把 2,457 个媒体文件全部通过扩展备份页的 File System Access API 写入
用户选择目录；服务器上的 16.09 GB 结果由同一登录会话和同一下载/校验策略的
真实执行器保存，不能冒称为扩展 UI 已完成全量目录验收。下一步必须在 VNC 中
通过备份中心选择目录，完成小画布的扩展端到端写入验收，再扩大到大画布。
