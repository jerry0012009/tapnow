# TapNow 工作空间本地备份方案

## 1. 文档目的

本文只讨论设计和实施计划，不实现工作空间批量下载，也不改变当前副驾驶功能。
目标是让插件后续能够在用户有权访问的范围内，有序保存 TapNow 的项目、画布、
节点、连线、文本、媒体及可追溯的版本信息。

这项能力有两个用途：

1. 保存用户和团队的创作数据资产，能够检查完整性、暂停、恢复和增量同步。
2. 在获得团队明确同意并完成脱敏后，为后续 learning、踩雷点总结和 preference
   分析提供结构化数据来源。

数据备份和 learning 数据管线必须分开。备份优先保证忠实、可恢复，不因为学习
索引而改写或丢弃原始内容。

## 2. 目标与非目标

### 目标

- 备份当前用户实际有权访问的团队项目和个人项目。
- 保留项目/画布层级、节点字段、节点直接关系和所有可发现的媒体引用。
- 对大画布正确处理 API 分页，禁止因服务端硬上限而静默截断。
- 原图优先下载；无法证明为原图时明确标记降级，不把缩略图冒充原图。
- 支持首次全量备份、增量同步、失败重试、断点续传和本地状态展示。
- 提供可验证的 manifest、内容哈希、计数和引用闭包。
- 在用户界面中区分“未备份、备份中、已完成、部分完成、发现变更、失败”。

### 非目标

- 不绕过 TapNow 的登录、权限、配额或安全机制。
- 不抓取当前用户不可见的项目，不默认备份全站或其他组织。
- 不把 access token、Cookie、API key 或浏览器 profile 写入备份。
- 不默认修改、删除、运行或重新生成 TapNow 节点。
- 不把未经同意的团队素材直接上传到第三方 learning 服务。
- 不承诺网页内部接口永久稳定；每次运行都要记录版本和接口行为。

## 3. 真实环境调研结果

测试环境为已登录的真实 Chrome 和 TapNow 页面，测试日期为 **2026-09-08
(Europe/Berlin)**。本轮仅做页面读取、接口结构观察和一个媒体对象的元数据/
Range 探测，没有执行生成、编辑、删除或批量下载。

### 3.1 已验证事实

| 能力 | 真实验证结果 | 对设计的影响 |
| --- | --- | --- |
| 团队项目根列表 | `GET /api/canvas/v1/canvases?offset=0&limit=20&sort_by=updated_at&sort_order=desc&with_total=true&scope=team_shared&parent_filter=root_only` 返回 7 个项目和 `total=7` | 第一阶段可从根画布列表开始枚举 |
| 项目列表字段 | 列表项包含 `id`、`name`、`updated_at`、`child_canvas_count`、`nodes`、`connections`、`preview_image`、共享和组织字段 | 可显示项目状态，但不能只依赖封面或预览字段 |
| 画布快照 | `GET /api/canvas/v1/canvases/{id}?with_nodes=true&with_connections=true` 返回完整结构；抽查画布含 1,238 节点、1,242 连线 | 可作为快速快照和对账基线 |
| 节点分页 | `/nodes?limit=1000&include_relations=true` 实际返回 500 条、`has_more=true` 和 `next_cursor` | 必须按游标循环，不能把请求 limit 当返回保证 |
| 连线分页 | `/connections?limit=20` 返回 20 条、`has_more=true` 和 `next_cursor` | 连线也必须完整翻页 |
| 节点字段 | 包含 `id`、`canvas_id`、`type`、`data`、位置、尺寸、父节点、创建/更新时间等 | 原始节点 JSON 应保留，规范化索引另行生成 |
| 媒体下载 | `files.tapnow.media` 的真实媒体对象支持 `HEAD`、`ETag`、`Last-Modified` 和 Range；探测到 `206` 及 `Content-Range` | 可实现大小预检、断点续传和内容校验 |
| 媒体鉴权边界 | 主站 API 使用 Bearer；媒体请求不能复用主站 Authorization，需带主站 Referer | 下载器必须分离 API 请求头和媒体请求头 |
| 页面动态加载 | 项目页和画布页通过 fetch/XHR 加载；打开大画布可能触发节点测量状态的持久化 | 备份优先 API-first，减少打开大量画布造成的副作用 |

### 3.2 尚未证明的能力

以下能力不能在计划阶段当成已支持，实施时必须加入真实验收：

- 根画布的 `child_canvas_count` 与子画布枚举的确切接口和分页语义。
- 画布历史队列是否能稳定列出所有历史版本和全部派生资源。
- 某个媒体 URL 是否对应原始上传对象，而不是缩略图、预览图或处理后的版本。
- 不同媒体类型（视频、音频、超大图片）的 Range、过期、权限和大小限制。
- 生成任务的所有提交、流式事件、轮询和最终持久化事件是否覆盖每一种节点类型。
- 协作 WebSocket/Yjs 在团队项目中的启用条件及历史恢复能力。
- 删除项目、删除节点和权限变化在列表/详情 API 中的可观测延迟。

## 4. 概念模型

备份格式按以下关系组织，不把一个网页截图当作项目备份：

```text
Workspace / Organization
  └─ Project (TapNow 根画布或项目集合)
      └─ Canvas
          ├─ Node
          │   ├─ input / prompt / text / params / task status
          │   ├─ current output
          │   └─ Asset references
          ├─ Connection (source -> target)
          └─ History / derived variants
                └─ Asset
```

插件内部应给每个对象保留：

- TapNow 原始 ID。
- 所属 canvas/project ID。
- 对象类型和来源接口。
- `created_at`、`updated_at`（若存在）。
- 首次发现时间、最后核对时间和备份运行 ID。
- 原始 JSON 的哈希，便于增量判断和审计。

## 5. 推荐备份目录和文件格式

第一期建议输出到用户明确选择的本地目录，而不是只放在 Chrome 下载目录。
Chrome 扩展可用 File System Access API 让用户选择目录；若浏览器权限或长任务
稳定性不足，则由本地 companion/桌面 agent 执行文件写入。

建议目录：

```text
tapnow-backup/
  manifest.json
  workspace.json
  projects/
    <project-id>/
      project.json
      canvases/
        <canvas-id>/
          canvas.json
          nodes.ndjson
          connections.ndjson
          relations.json
          assets/
            manifest.ndjson
            by-sha256/
              <sha256>.<ext>
          history/
            manifest.ndjson
          raw/
            optional-api-responses/
  snapshots/
    <run-id>.json
  checksums.sha256
  sync-state.json
  logs/
    <run-id>.jsonl
```

### 5.1 文件职责

- `manifest.json`：备份格式版本、工具版本、TapNow 版本、组织范围摘要、运行
  时间、完成级别、项目/画布/节点/连线/媒体计数。
- `workspace.json`：用户选择的 scope、组织标识的脱敏摘要和项目清单；不写 token。
- `project.json`：项目名称、ID、权限可见性、更新时间、子画布数量及枚举状态。
- `canvas.json`：画布元数据和接口原始字段，保留服务端未知字段以便未来迁移。
- `nodes.ndjson`、`connections.ndjson`：一行一个原始对象，适合大画布流式写入，
  避免将整个项目同时放进扩展内存。
- `relations.json`：由节点/连线分页结果核对生成的关系索引；原始关系字段仍保留。
- `assets/manifest.ndjson`：每个资源的来源节点、来源字段、引用顺序、角色、URL
  规范化信息、HTTP 元数据、文件哈希、下载状态和降级原因。
- `by-sha256/`：按内容 SHA-256 去重保存文件；同一文件被多个节点引用时只保留
  一份实体文件。
- `history/manifest.ndjson`：历史版本、变体和派生资源的索引；是否下载由备份
  范围开关决定。
- `snapshots/`：每次运行的摘要，用于比较项目数量、节点数量、媒体状态和变更。
- `sync-state.json`：游标、已完成对象、失败原因、ETag、最后成功时间和待重试任务。
- `checksums.sha256`：对所有规范文件和已下载媒体做最终校验。
- `raw/`：可选的完整 API 响应取证副本，默认只在本地私有备份启用。

NDJSON 中每条记录都应包含 `schema_version` 和 `source`，这样即使 TapNow
字段变化，也能区分原始字段和本地推导字段。

## 6. 媒体和原图策略

### 6.1 发现范围

不能只下载节点的 `src`。实施时应从节点数据中统一发现并分类：

- `currentSourceFileId` 和对应原始媒体 URL。
- `src`、`options`、`__metadata.url`。
- 节点当前产物、输入引用和直接上游节点媒体。
- `historyLocalQueues`、`historyLocalQueueMetadata` 中的历史变体。
- 画布封面、项目预览仅作为项目预览资源，不能覆盖创作原图。

每个 URL 必须关联 `sourceNodeId`、字段路径、资源角色和引用顺序。一个节点
有多张图时，保存 `image-1`、`image-2` 等稳定序号，并保留 TapNow file ID，
避免“哪张图是哪张图”只能靠文件名猜测。

### 6.2 原始对象优先

下载器的优先级应是：

1. 能从 `currentSourceFileId` 或明确 file ID 得到的原始对象。
2. 节点数据中无缩略图参数的原始 `src`/媒体 URL。
3. 可验证的高分辨率派生对象。
4. 仅作预览的缩略图或压缩图。

URL 上的 `tap_mx`、`small`、`thumbnail` 等参数不能简单删除后就宣称得到
原图。每次下载记录：

- 最终 URL 和规范化 URL。
- `Content-Type`、`Content-Length`、`ETag`、`Last-Modified`。
- 文件 SHA-256、实际字节数、像素尺寸或媒体时长（可解析时）。
- 原始/派生判断依据。
- 若只能拿到衍生文件，记录 `derivative-only` 和原因。

如果原图不可访问，默认任务状态为“部分完成”，允许用户选择保留可用衍生图
作为预览，但 UI 和 manifest 必须明确显示缺失原图，不能伪装为完整备份。

### 6.3 大文件、断点和并发

- 先 `HEAD`，若不可靠则用 `Range: bytes=0-0` 预检。
- 使用临时文件和分块 Range 下载，成功后再原子改名。
- 断点状态写入 `sync-state.json`，进程中断后从已确认字节继续。
- 按媒体域设置低并发和指数退避，避免对团队项目造成突发流量。
- 内容哈希完成前不能把文件标记为已备份。
- 对重复 URL 和重复 SHA-256 去重，但保留每一个引用关系。
- 媒体下载不携带主站 Bearer token，只使用媒体域实际需要的 Referer/会话
  头，并在日志中脱敏。

## 7. 完整性等级

备份结果应提供分层状态，而不是只有一个“下载成功”：

- `metadata-complete`：项目和画布元数据完整。
- `graph-complete`：节点、连线、分页游标已耗尽，引用的节点 ID 可解析。
- `text-complete`：节点输入、文本输出和模型参数已保存。
- `asset-complete`：发现的当前资源均已下载并通过大小/哈希校验。
- `history-complete`：选择范围内的历史版本和派生资源均已处理。
- `complete`：选择范围的所有层级均完成，且没有未解释的缺失。
- `partial`：存在明确记录的权限、过期、原图不可得、超限或网络失败。

每个项目和整个工作空间都要做 reconciliation：

1. 列表 `total` 与实际遍历项目数一致。
2. 节点/连线分页结束后，返回数与快照计数交叉核对；不一致则报警。
3. 每条 connection 的 source/target 节点存在，或被记录为孤儿关系。
4. 每个媒体引用都能在 asset manifest 找到，且 material-to-file 关系完整。
5. 下载文件字节数、哈希和 manifest 一致。
6. 重跑同一快照不应产生重复实体文件，只产生可解释的引用和运行记录。

## 8. 增量同步和备份状态

首次运行做预扫描，不立即下载全部数据。预扫描展示：

- 项目/画布数量。
- 节点、连线和媒体引用数量。
- 预计字节数及无法估算的资源数量。
- 需要全量下载、可复用、已存在但待校验和失败重试的资源。

后续运行使用多重判断：

- API 游标和服务端 `updated_at`。
- 原始节点/连线 JSON 哈希。
- 媒体的 file ID、ETag、Last-Modified、Content-Length 和 SHA-256。
- 上一次运行的删除/权限快照，使用 tombstone 标记消失对象。

不能单独依赖 `updated_at`，因为页面打开可能写入测量或状态字段。建议保存
append-only run snapshots，再生成当前视图，便于发现“内容没变但页面状态变了”。

项目列表 UI 建议显示：

| 状态 | 含义 |
| --- | --- |
| 未备份 | 本地没有该项目的成功快照 |
| 备份中 | 有可恢复的队列任务 |
| 已完成 | 选择范围内完整性通过 |
| 部分完成 | 存在已记录的缺失或降级媒体 |
| 有变更 | 云端哈希/时间/资源清单与本地不同 |
| 失败 | 本次没有形成可用快照，需查看原因 |

## 9. 插件形态建议

副驾驶浮窗应继续聚焦当前节点；工作空间备份属于长任务，不应塞进节点审阅
面板。建议新增一个独立的“备份中心”入口，优先放在 TapNow 项目列表页或
扩展 Side Panel：

1. 选择范围：当前画布、项目、团队项目、个人项目。
2. 预扫描：只读枚举、估算和完整性风险。
3. 选择内容：当前产物、直接引用资源、全部历史/变体、预览资源。
4. 选择目录并开始：展示速度、剩余数量、字节数和失败项。
5. 暂停/恢复/重试：队列可持久化，关闭弹窗不丢任务。
6. 完成报告：完整性等级、缺失原图、孤儿关系、哈希校验和变更摘要。

### 浏览器扩展还是本地 companion

第一期可用扩展完成 API 枚举和小规模单画布导出，但团队大项目的长期任务
更适合“扩展负责授权和控制 + 本地 companion/桌面 agent 负责下载”。原因是：

- MV3 service worker 可能被挂起，不能把数十 GB 下载状态只放内存。
- File System Access API 需要用户授权，并受页面/浏览器生命周期影响。
- 大文件、Range、临时文件和原子改名在本地进程中更容易可靠实现。
- 扩展仍可提供项目状态、暂停和错误可视化。

## 10. 与 learning / preference 的边界

建议备份层和学习层采用单向、显式的导入：

```text
原始备份 -> 用户选择/脱敏 -> 规范化索引 -> learning/preference 数据集
```

学习索引至少应保留：

- 节点类型、输入/输出关系、引用素材顺序。
- 提示词版本、模型参数和结果状态。
- 用户明确标记的好例、坏例、修改原因和团队风格标签。
- 数据来源、时间、权限范围和脱敏状态。

默认不上传原图和原始提示词。若团队确认要使用，应提供项目/节点级选择、
脱敏规则、可删除索引和审计记录。备份删除不应自动等同于删除外部学习数据，
两者必须有独立的生命周期。

## 11. 分阶段实施

### P0：确定性单画布备份

- API-first 读取画布元数据、节点、连线和当前媒体。
- 节点/连线游标分页，输出规范目录、manifest 和 SHA-256。
- 原图/衍生图明确分类。
- 真实大画布、重复媒体、失败重试和断点测试。

### P1：项目枚举和备份状态

- 接入团队/个人 scope。
- 验证子画布枚举和权限变化。
- 项目列表预扫描、容量估算、状态徽标和单项目任务队列。

### P2：大文件与增量

- Range 断点、低并发、ETag/哈希复用。
- 全历史/变体开关。
- 删除检测、tombstone、重跑 reconciliation。

### P3：工作空间级调度和学习导入

- 可暂停的 workspace 队列和计划任务。
- 本地索引检索、偏好标签和踩雷点总结。
- 脱敏后的可选团队 learning 管线。
- 在取得正式授权后评估自有后端或企业存储。

## 12. 验收测试矩阵

| 场景 | 必须证明 |
| --- | --- |
| 7 个团队根项目 | 列表总数、分页和权限范围一致 |
| 1,000+ 节点画布 | 节点/连线游标耗尽，无静默截断 |
| 多层直接关系 | 每条边和引用序号可回溯到源节点 |
| 一个节点多图片 | `Image 1`、`Image 2` 与 file ID、来源节点稳定对应 |
| 25 MB 以上原图 | 原字节数、SHA-256、尺寸和可恢复下载一致 |
| 同 URL 多次引用 | 实体文件去重，引用不丢失 |
| 缩略图与原图并存 | 预览与原图分别记录，不能互相覆盖 |
| 断网/关闭 Chrome | 任务可恢复，临时文件不会被误标完成 |
| 资源 401/403/404 | 记录原因并显示部分完成，不伪装成功 |
| 项目或节点删除 | 下一次同步生成 tombstone 和差异报告 |
| 页面懒加载 | 不依赖滚动到所有节点，API 抓取结果独立核对 |
| TapNow 前端升级 | 记录版本，字段/状态变化触发兼容性告警 |
| learning 导入 | 未选择的数据不会上传，脱敏和来源可审计 |

## 13. 需要确认的产品决策

建议先确认以下事项，再进入 P0 开发：

1. **目的地**：第一期是否采用用户选择的本地目录；后续是否需要 NAS、S3、
   企业盘或桌面 companion。
2. **历史范围**：默认只备份当前节点产物和当前直接引用资源，还是默认包含
   全部 `historyLocalQueues` 历史版本。
3. **原图失败策略**：允许保留标记为 `derivative-only` 的预览并完成部分备份，
   还是遇到原图缺失就让项目任务失败。
4. **团队权限**：是否只备份当前账号可见内容；管理员统一备份需要额外授权和
   审计。
5. **学习范围**：learning 是否默认关闭；哪些项目/节点允许进入学习索引；
   是否需要本地脱敏和单独保留期限。
6. **历史删除语义**：云端消失的对象是仅标 tombstone，还是允许用户确认后
   从本地删除。

在这些决策明确前，不建议直接开发“团队一键全部下载”，因为最容易出现的
问题不是下载按钮本身，而是权限边界、历史范围和原图缺失被错误地报告为完整。
